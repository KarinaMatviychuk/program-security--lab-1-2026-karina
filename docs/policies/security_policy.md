# Політика безпеки проєкту (Security Policy)
**Проєкт:** Auth & Identity Service  
**Версія:** 1.0.0  
**Автор:** Каріна Матвійчук (група ІПЗ-23-1)  
**Статус:** Active  

---

## 1. Мета та область дії (Purpose & Scope)
Ця Політика безпеки визначає обов'язкові правила, принципи та обмеження, спрямовані на забезпечення безпеки розробки, експлуатації та супроводу модуля автентифікації Auth & Identity Service.
Політика поширюється на вихідний код у репозиторії, конфігураційні файли, CI/CD-пайплайни, середовище розробки та всіх розробників проєкту.

## 2. Ролі та відповідальність (Roles & Responsibilities)
* **Lead Developer / Security Officer (Каріна Матвійчук):** відповідає за затвердження політики, перегляд коду (Code Review), управління секретами та реагування на вразливості.
* **Contributors / Developers:** зобов'язані дотримуватися вимог цієї політики під час написання коду, створення комітів та підключення зовнішніх залежностей.

## 3. Принципи безпеки (Security Principles)
* **Principle of Least Privilege (Мінімальні привілеї):** доступ до ресурсів та баз даних надається лише в обсязі, необхідному для виконання функції.
* **Defense in Depth (Багаторівневий захист):** перевірка безпеки здійснюється на рівнях вхідних даних, бізнес-логіки та збереження даних.
* **Secure by Default:** усі безпекові налаштування за замовчуванням є максимально строгими (наприклад, заблокований доступ при виникненні помилки).
* **Zero Trust Secrets:** заборонено зберігати паси, ключі, токени та секрети у вихідному коді або репозиторії Git.

## 4. Безпечне середовище розробки та Git
* **Автентифікація:** доступ до віддаленого репозиторію GitHub дозволено виключно за протоколом SSH з використанням асиметричних ключів (Ed25519).
* **Захист гілок:** прямий push у гілку `main` заборонений. Усі зміни вносяться через Pull Requests із обов'язковим переглядом коду.
* **Управління секретами:** усі конфігураційні секрети передаються виключно через змінні оточення (`.env`), які додані до `.gitignore`.

## 5. Безпечна реалізація та захист даних
* **Паролі:** заборонено зберігати паролі у відкритому вигляді. Використовується стійке криптографічне хешування (Argon2id або bcrypt) із додаванням солі.
* **Валідація вхідних даних:** усі вхідні дані підлягають суворій перевірці типів, довжини та формату (строга біла типізація) для запобігання атак ін'єкцій.
* **Обробка помилок:** системи не повинні повертати детальні стеки помилок (Stack Trace) або технічну інформацію зовнішньому користувачеві.

## 6. Перевірка безпеки та управління вразливостями
* **Аналіз залежностей:** підключені зовнішні бібліотеки повинні регулярно перевірятися на наявність відомих вразливостей (CVE).
* **Реагування на вразливості:** у разі виявлення критичної вразливості критичне оновлення (hotfix) розробляється та розгортається протягом 24 годин.
